# ADR-0079: A deterministic C4 view (the Architecture tab)

- Status: accepted (P10)
- Context: infra cannot be drawn under the map's components. One deployment unit can host
  functionally distant components, and every cloud has its own vocabulary. A C4 container view
  is the common language, and it can be derived instead of drawn.

## Decisions

1. **Derived, never drawn by hand.** `c4.derive(graph, statuses, links)` is a pure function per
   infra environment (`''` without infra), stored as `c4_elements` / `c4_relations`.
   - Context level:
     - the system;
     - persons from user-story actors (`attrs.actor`, deduplicated by normalized name);
     - external systems from code `external_service` / `llm_endpoint` nodes.
   - Container level:
     - deployment units, listing the code containers they deploy;
     - website buckets as `static_site`;
     - managed datastores, queues, buckets and schedulers;
     - code containers that no unit deploys (`undeployed`, `ambiguous`, or `unknown` without
       infra).
     Without infra, the code side's datastores and queues stand in for the data row.
   - Relations:
     - code edges aggregated to elements (calls, reads, writes, publishes, consumes, invokes);
     - `wires` (with env var names) and `references` between infra elements (dropped when a wire
       joins the same pair);
     - person → container (`uses`) where a story's requirement pairs with code inside.
   - Components are the map: an element card offers "open in map".
2. **Each container element carries:**
   - the roll-up of the statuses of the requirements linked to its code (`coverage`,
     `coverage_worst`);
   - its infra status;
   - unwired env var names;
   - the NFRs of spec components mapped to it, labeled "NFR (checked against infra in a later
     phase)". There are no NFR-vs-infra checks in P10.
3. **Layout** (`c4_layout`, deterministic): rows persons / units / data / external, plus the
   system boundary as a slab. An element keeps its row and slot across epochs; new elements take
   the lowest free slot; removed ones leave a gap. Two epochs of the brownfield fixture keep
   ≥ 95% of common elements in place (test).
4. **Rendering.** SVG with theme tokens, compact rather than UML-looking. Tabs: Map | Architecture.
   Selection syncs both ways. The environment selector switches findings.
5. **Exports.** `ad2v c4 <file> [--env] --format structurizr|json` writes a Structurizr DSL
   workspace (context + container views, tags carry kind and infra status) or JSON. Both are
   deterministic, with a golden for brownfield-es prod.
6. **MCP and chat.**
   - a read-only `ad2v_architecture` tool (elements, relations, findings per environment; names
     wrapped as untrusted text; no secrets exist to return);
   - a `c4` intent for `ad2v_show`, honored by the MCP App and the viewer;
   - `ad2v_overview` reports infra counts and findings;
   - retrieval adds kind and infra-status words (the deployment unit ranks first for "which cloud
     run service runs the api").
